> 线上地址：https://hxh554.github.io/qingzhang/
> 代码仓库：https://github.com/hxh554/qingzhang
> 数据库：Supabase 免费版（`kkujzunjoznrwvlvowrw.supabase.co`，新加坡区）

---

## 一、一句话说清这套方案

**前端代码放在 GitHub Pages（免费静态托管），数据放在 Supabase（免费的 Postgres + 登录 + 实时推送），两者靠浏览器里的 JS 直连。**

所以：不需要买服务器、不需要写后端接口、不需要运维。两个人各自打开同一个网址、登录不同账号、绑定同一本账，就能互相看到对方记的每一笔。

关键认知：**GitHub Pages 只存代码，不存任何数据。** 数据一行都不经过 GitHub。真正“共享”的部分全在 Supabase 的数据库里。

## 二、三层架构

### 第 1 层：客户端（手机 / 电脑浏览器）

React 单页应用，构建后是一堆 `.html` / `.js` / `.css` 静态文件。

本地还有一层 **IndexedDB 缓存**（用 Dexie 包了一层）。所有页面都从 IndexedDB 读数据——不是从网络读。这是"打开就秒开、断网也能记账"的原因。

### 第 2 层：GitHub Pages（只托管代码）

- 免费、公开仓库、自带 HTTPS
- 构建产物 `dist/` 由 GitHub Actions 自动上传
- 只负责把 `index.html` 和 JS 发给浏览器，之后就没它的事了

### 第 3 层：Supabase（真正的数据层）

三个能力拼起来：

| 能力 | 作用 |
|---|---|
| **Auth** | 邮箱 + 密码登录，签发 JWT |
| **Postgres + RLS** | 数据存储；行级安全策略保证"只有这本账的成员能读写" |
| **Realtime** | 数据库有变更时，主动推给在线的客户端 |

## 三、一次记账的完整链路

```
你点「记一笔」填 66.66
   ↓
① 立即写入本机 IndexedDB           ← 页面瞬间刷新，不等网络
   ↓
② Dexie hook 把这条写操作放进队列
   ↓
③ 后台异步 → REST 写进 Supabase    ← 走你的登录 token，RLS 校验成员身份
   ↓
④ Supabase 通知所有订阅了这本账的客户端
   ↓
⑤ 家人手机的 IndexedDB 被更新 → 页面自动出现 66.66
```

**这中间任何一步断了，体验都不会崩**：
- 没网：①成功，②排队，等网络回来自动重推
- 推送通道断了：⑤走轮询兜底（见下）

## 四、实时同步的两个通道

这是这套方案里唯一"不标准"的地方，也是最关键的地方。

### 通道 A：Realtime 推送（首选）

Supabase 的 WebSocket，正常情况下 1 秒内到。代码在 `src/lib/sync.ts` 的 `subscribe()`：

```ts
channel = supabase.channel('qz:' + bid)
  .on('postgres_changes', { event: '*', schema: 'public', table: 'txs', filter: `book_id=eq.${bid}` }, handler)
```

### 通道 B：12 秒轮询兜底（保命）

**国内网络到 Supabase 的 WebSocket 经常被掐断**，推送收不到是常态。所以加了 `startPolling(bid, 12000)`：

- 每 12 秒拉一次全量数据
- 拉回来先算内容签名，**和上次一样就什么都不写**（避免无意义刷新）
- 手机从后台切回前台（`visibilitychange`）立即拉一次

代价：最坏情况对方晚十几秒看到。对家庭记账完全够用。

### 防死循环：suppress 计数器

远端数据写进本地时会触发 Dexie 的写 hook → 又会被推回云端 → 又触发远端 → 无限循环。

解决办法是一个 `suppress` 计数器：从远端应用变更时先加一，hook 看到计数器非零就跳过不入队，写完再减一。

## 五、多人共享的权限模型

### 表结构（`supabase/schema.sql`）

```
books              账本
book_members       谁在哪本账里、什么角色（owner / member）
book_invites       6 位邀请码，24 小时有效
members            家庭成员（账本内的"人"，和登录账号是两回事）
categories / accounts / projects / merchants / txs    业务数据
```

每张业务表都带 `book_id`。

### 权限判断（全部在数据库里，前端绕不过）

```sql
-- 我是不是这本账的成员？
is_book_member(bid)
-- 我在这本账里是什么角色？
book_role(bid)
```

所有表的 RLS 策略都长这样：

```sql
create policy "member read" on txs for select
  using (is_book_member(book_id));
```

前端哪怕被人改了 JS、伪造请求，也只能读到自己是成员的账本。**安全性不依赖前端，依赖数据库。**

### 加入一本账的流程

```
你：设置 → 云端同步 → 生成邀请码        → 云端写一条 book_invites（A92933）
家人：设置 → 云端同步 → 输入 A92933      → 调 RPC join_book(code)
                                          → 校验未过期 → 写入 book_members
                                          → 之后他读到的就是同一本账
```

### 一个容易踩的坑：当前账本怎么定

客户端本地固定用 `BOOK_ID = 'book_default'`，云端账本 id 存在 `localStorage['qz_cloud_book']`。

`ensureBook()` 的取值顺序必须是：**先看 localStorage 记住的那个 → 再取"最近加入"的一本**。

早先写成取 `list[0]`（最早加入的），结果家人注册时先自动建了自己的空账本，再加入你的账——`list[0]` 永远是他自己那本空的，于是怎么等都看不到你的数据。这个 bug 折腾了最久。

## 七、部署流程（一次性，已经做完了）

1. **Supabase 建项目** → SQL Editor 整段执行 `supabase/schema.sql`
2. **Authentication → Providers → Email** 关掉 `Confirm email`（自用省掉收邮件）
3. **GitHub 建 Public 仓库** → 推代码
4. **仓库 Settings → Pages → Source 选 `GitHub Actions`**（⚠️ 必须手动点一次，workflow 自己开不了）
5. 等 Actions 跑完 → 访问 `https://<用户名>.github.io/<仓库>/`

云端参数不用配 Secrets，直接写在 `deploy.yml` 的构建环境里：

```yaml
- run: npm run build
  env:
    VITE_SUPABASE_URL: https://kkujzunjoznrwvlvowrw.supabase.co
    VITE_SUPABASE_ANON_KEY: sb_publishable_LIHY...
```

> 为什么不藏这两个值？`VITE_` 开头的变量本来就会被打包进前端 JS，打开浏览器就能看到。Supabase 的 publishable key 设计上就是公开的，安全性靠 RLS，不靠藏 key。**但 `service_role` key 绝对不能放前端。**

## 九、这套方案踩过的坑（备忘）

| # | 现象 | 真实原因 | 解决 |
|---|---|---|---|
| 1 | `remote: Repository not found` | remote 用了 Gitee 的账号名，GitHub 账号是另一个 | 确认 GitHub 用户名后用 `git remote set-url` |
| 2 | `Failed to connect to github.com port 443` | 机器上跑着深信服 aTrust（银行零信任），掐了 github.com 的 HTTPS；baidu/gitee 都正常 | 改走 `ssh.github.com:443`（SSH 无明文 SNI，能穿过去） |
| 3 | 浏览器登录后卡在 `127.0.0.1:xxxxx` 白屏 | GCM 的 OAuth 回调页渲染不出来，但**认证其实已完成** | 无视它，直接回终端 |
| 4 | Actions 在 `configure-pages` 失败 | 仓库 Pages 从未启用；给 action 加 `enablement: true` 也绕不过 | 去 Settings → Pages 手动选 `GitHub Actions` |
| 5 | 家人看不到对方的记录 | `ensureBook()` 取到了自己那本空账本 | 优先 localStorage 记住的账，否则取最近加入的 |
| 6 | 统计数据变 `NaN` | PostgREST 把 `numeric` 返回成字符串 | `norm()` 统一强转 Number |
| 7 | 首次登录卡十几秒 | 把本地 188 条演示数据全推上云 | 首次只推骨架表；流水用「上传本机流水」手动推 |

SSH 那套配置（因为银行 VPN 环境才需要）：

```
# ~/.ssh/config
Host github.com
  HostName ssh.github.com
  Port 443
  User git
  IdentityFile ~/.ssh/id_ed25519
```

> 这条隧道也是时通时不通，`git push` 报 timeout 就**原样再敲一次**，不要改配置。

## 十、成本与限制

| 项 | 免费额度 | 够不够用 |
|---|---|---|
| GitHub Pages | 100 GB/月流量，1 GB 站点 | 家庭记账绰绰有余 |
| Supabase 数据库 | 500 MB | 一笔流水约 200 字节，能存两百万笔 |
| Supabase 月活用户 | 50,000 | 够 |
| Supabase 闲置策略 | 免费项目 **7 天无请求会被暂停** | 天天记账不会触发；长期不用需去后台点一下恢复 |

已知限制：

- **国内访问 `github.io` 不稳定**，有时慢有时打不开。要长期稳定给家人用，把 `dist/` 传到阿里云 OSS / 腾讯云 COS 的静态网站托管（域名已备案），或挂 Cloudflare 加速。
- **WebSocket 推送在国内不可靠**，实际体验是"秒级到十几秒级"，靠轮询兜底。
- 前端包 1.1 MB（gzip 后 350 KB），主要是 ECharts。首次打开稍慢，之后走缓存。
